# חלק א' — סקירה כללית של המערכת

## מה המערכת עושה
מכונת קצה־קו לבדיקת מיסבי מנוע (King 457). לכל עצם שעובר על המסוע מתבצעות שתי בדיקות בלתי תלויות:

1. **ניתוח תמונה (Machine Vision)** — צילום באור ירוק ולבן, עיבוד, והכרעה תקין/פסול.
2. **מדידת עובי** — שני חיישני לייזר (עליון/תחתון) מודדים את העצם תוך כדי תנועה; מחושבים עובי ממוצע, P2P וקוניות, ומתקבלת הכרעה.

תוצאות שתי הבדיקות נשלחות לבקר (PLC), שמבצע את המיון הפיזי בפועל.

## הקבצים והתלויות
- `457_test.py` — נקודת הכניסה (`python 457_test.py`). מייבא:
  - `thickness_Module_V3_w as thck` — מודול העובי (המסמך הזה).
  - `mv457_MachineVision as mv` — מודול ניתוח התמונה (לא מכוסה כאן).
  - `Utils` — עזרי SQL.
  - `pyModbusTCP` — תקשורת Modbus TCP לבקר.
- `thickness_Module_V3_w.py` — מודול עצמאי headless (ללא UI משלו). ה-UI החיצוני מקבל ממנו **רק תמונת PIL + מדדים + קוד תוצאה**.

## קבצי קונפיגורציה (תיקיית `config/`)
| קובץ | נטען ע"י | תוכן |
|------|----------|------|
| `config457.json` | `Cfg_` (קוד ראשי) | מזהה תחנה, IP/פורט בקר, מרווח live-sign, מחרוזות SQL, תיקיית MV, סיסמה |
| `Job_settings.json` | `Job_settings_` | כותרת העבודה: מספר הזמנה, מק"ט, כמות, מונה עצמים, pack job נוכחי |

## ה-threads וזרימת הנתונים
ב-`__main__` עולים ארבעה threads (כולם `daemon=True`) ואז ה-UI הראשי:

```
T4 (PLC)  ← RegsToPlc[] →  T2 (MV) , T3 (Thickness)
T1 (Engraving imgs) , T2 (MV) , T3 (Thickness)  →  Job_settings.pilN  →  EL_UI._refresh (כל 200ms)
```

- **T1** — תמונות חריטה (ממלא `pil1`).
- **T2** — מכונת מצבים של ה-MV (ממלא `pil2`/`pil22`, כותב ל-`RegsToPlc[1..4]`).
- **T3** — עוטף את מודול העובי (ממלא `pil3` + מדדים, כותב ל-`RegsToPlc[5]`).
- **T4** — התקשורת היחידה עם הבקר: שולח את `RegsToPlc` וקורא `RegsFromPlc`.
- **EL_UI** — ה-thread הראשי; לולאת רענון שמושכת את כל ה-`pilN` למסך.

**עיקרון חשוב:** רק T4 מדבר עם הבקר. כל שאר ה-threads "משדרים" לבקר ע"י כתיבה למערך `RegsToPlc` (תחת `RegsLock`), ו-T4 דואג לשליחה בפועל.

## מצב משותף ונעילות (שורות 73–80)
- `Cfg` — אובייקט קונפיג גלובלי.
- `RegsToPlc = [0]*20` — רגיסטרים לכתיבה לבקר (Py→PLC).
- `RegsFromPlc = [0]*40` — רגיסטרים שנקראו מהבקר (PLC→Py).
- `RegsTemp = [0]*20` — חוצץ עזר.
- `RegsLock` — מגן על גישה ל-`RegsToPlc`.
- `log_lock` — מסדר כתיבה ל-`system_log.txt`.

## מפת הרגיסטרים (כפי שהקוד משתמש בה בפועל)
> ⚠️ **אזהרת תחזוקה:** ה-docstring בראש הקובץ (שורות 82–105) מתאר מיפוי **ישן ולא תואם** למה שהקוד עושה. המיפוי הנכון הוא זה שבהערות שליד `T4_plc_flush` (שורות ~407–415) ושמשתמשים בו בפועל ב-T2/T3:

**Py → PLC (`RegsToPlc`):**
| רגיסטר | משמעות |
|--------|--------|
| `[0]` | `1` = live-sign |
| `[1]` | `1` = מסוע קדימה, `2` = אחורה, `3` = עצור |
| `[2]` | `1` = אור ירוק דלוק, `2` = ירוק כבוי |
| `[3]` | `1` = אור לבן דלוק, `2` = לבן כבוי |
| `[4]` | תוצאת ניתוח תמונה (מקור: `mv.Cfg_mv.sttprog`) |
| `[5]` | **תוצאת עובי (`THK_RESULT_REG`): `0`=כלום, `1`=תקין, `2`=נמוך, `3`=גבוה, `4`=קוניות גבוהה** |
| `[13]` | **סטטוס כיול עובי (`CAL_STAT_REG`): `0`=idle, `1`=מודד (אל תזוז), `2`=מדיד 1 הסתיים (אפשר לזוז), `3`=כיול תקין, `4`=כיול נכשל** |

**PLC → Py (`RegsFromPlc`):**
| רגיסטר | משמעות |
|--------|--------|
| `[20]` | סטטוס: `0`=שגיאה, `1`=ידני, `2`=אוטומט, `>10`=קוד שגיאה |
| `[21]/[22]` | מיקום ציר X / Y |
| `[23]` | סטטוס סרוו: `0`=null, `1`=מוכן, `2`=עובד, `3`=הסתיים |
| `[24]` | **פקודת כיול עובי (`CAL_CMD_REG`): `0`=idle, `1`=במדיד 1 מדוד, `2`=במדיד 2 מדוד (חישוב אוטומטי אחריו)** |
| `[25..39]` | פנוי |

> מספרי הרגיסטרים (`THK_RESULT_REG=5` לעובי, `CAL_STAT_REG=13` לסטטוס כיול, `CAL_CMD_REG=24` לפקודת כיול) מוגדרים כקבועים בראש `457_test.py` וקלים לשינוי לפי מה שמוסכם עם מתכנת ה-PLC.

# חלק ב' — הקוד הראשי `457_test.py` (1513 שורות)

## 1. `Cfg_` / `Cfg` (שורות 26–73)
מחלקת קונפיג שנטענת מ-`config/config457.json` ב-init.
- שדות נשמרים: `WorkstationId, PlcTcpip, PlcPort, PlcLiveSignIntervalSeconds, SqlNt, SqlPri, MvFolder, Password`.
- `plc_connected` — דגל ריצה בלבד (לא נשמר ל-JSON); מתעדכן ע"י T4 ומוצג באינדיקטור ה-PLC ב-UI.
- `_load()` קורא את ה-JSON, `save()` כותב חזרה.
- מופע גלובלי יחיד: `Cfg = Cfg_()`.

## 2. `log(msg, level="INFO")` (שורות 107–117)
מנגנון הלוג המרכזי: בונה שורה עם חותמת זמן `HH:MM:SS.mmm [LEVEL] msg`, **מדפיס לטרמינל וגם מוסיף ל-`system_log.txt`** תחת `log_lock`. הרמות בשימוש: `INFO`, `STATUS`, `WARN`.

## 3. `Job_settings_` / `Job_settings` (שורות 119–185)
מצב העבודה והגשר בין ה-threads ל-UI.
- **תמונות PIL משותפות** (נכתבות ע"י threads, נקראות ע"י ה-UI): `pil1` (חריטה), `pil2` (תוצאת MV), `pil22` (MV חי), `pil3` (פאנל עובי).
- **מדדי עובי**: `thk_mean_mm, thk_p2p_um, thk_conicity_um`.
- **כותרת עבודה** (`JsonKeys`): `wo_order_number, wo_part_number, wo_order_quantity, wo_object_counter, current_pack_job`.
- **טבלאות**: `pack_jobs` (מ-xlsx), `spec` (מ-csv).
- `stop_event` — `threading.Event` משותף לעצירה מסודרת של כל ה-threads.
- `reload()` / `save()` — טעינה/שמירה מ/אל שלושת הקבצים.

## 4. עזרי תמונה (שורות 191–223)
- `Random_Image()` — בוחר תמונת חריטה אקראית מ-`icons/`, מקטין ל-thumbnail.
- `to_pil(im)` — ממיר PIL/ndarray ל-PIL. ⚠️ מטפל רק ב-grayscale ו-ndarray תלת-ערוצי; פורמטים אחרים (למשל RGBA) גורמים להחזרת `None` בשקט — נקודת תורפה ידועה.

## 5. ה-threads

### `T1()` (שורות 226–246)
מציג תמונת חריטה אקראית, ומחליף אותה כל ~1000 איטרציות. ממלא את `Job_settings.pil1`.

### `T2()` — מכונת המצבים של ה-MV (שורות 248–318)
לולאה ב-~20Hz שמנהלת מחזור צילום/ניתוח לכל עצם:
- **state 0 → 1**: זוהה עצם (`mv.img.status==3`) → `RegsToPlc[1]=3` (עצור מסוע), `log('conveyor was stopped')`.
- **state 1 → 2**: אור ירוק מוכן → שומר `img_G` לדיסק, מדליק לבן/מכבה ירוק, `log('green light img is saved')`.
- **state 2 → 3**: אור לבן מוכן → שומר `img_W`, מחזיר מסוע לתנועה, מפעיל `mv.run_prog` ב-thread נפרד, `log('start image processing...')`.
- **state 3 → 0**: העיבוד הסתיים → `RegsToPlc[4]=sttprog`, מרענן את `pil2`, `log('img processed done... OK/NOT OK', 'STATUS')`.

מעדכן את `pil22` (תצוגה חיה) כל 0.3 שניות כל עוד לא במצב עיבוד.

### `T3_thickness()` — *שונה*
1. יוצר `thck.ThicknessModule()` ומפעיל אותו (`start()`).
2. בלולאה כל 0.2 שניות: מושך `get_ui_packet()` → `pil3` + שלושת המדדים.
3. מושך `poll_new_result_code()`; אם חזר קוד (עצם חדש הושלם) — כותב `RegsToPlc[5]=code` ורושם `log('thickness verdict reg5=...', 'STATUS')`.
4. **כיול:** מכונת מצבים edge-triggered מול `RegsFromPlc[CAL_CMD_REG]` — מודד מדידים, מחשב/מחיל כיול, מדווח ל-`RegsToPlc[CAL_STAT_REG]` (רגיסטר 13, נפרד מתוצאת העובי), ומפרסם את המצב ל-`Job_settings.thk_cal`. ראה **חלק ד'**.
5. בעצירה — `ThckModule.stop()`.

### `T4_plc_flush()` — התקשורת עם הבקר (שורות 344–417) — *הפעיל*
ה-thread היחיד שמדבר עם הבקר.
- פותח `ModbusClient(host="192.168.3.169", ...)`. ⚠️ ה-IP **קשיח בקוד** ושונה מ-`Cfg.PlcTcpip` (`192.168.3.76`).
- אם יש ערך חיובי כלשהו ב-`RegsToPlc`: מעתיק תחת `RegsLock`, **מאפס** את `RegsToPlc`, ושולח 20 רגיסטרים; מיד אחרי השליחה קורא 40 רגיסטרים אחורה ל-`RegsFromPlc` (`_write_20_and_read_40`).
- אם אין מה לשלוח: שולח live-sign (`RegsToPlc[0]=1`) כל `PlcLiveSignIntervalSeconds`.
- האיפוס אחרי שליחה הוא מה שמייצר את התנהגות ה"פעימה": ערך נשלח פעם אחת ואז חוזר ל-0 — מתאים בול ל-`0 = כלום` של רגיסטר 5.

### `T4_plc_flush_1()` (שורות 420–502) — **לא בשימוש**
וריאנט חלופי (host `.76`, לוגיקת reconnect והשוואה ל-`LastSentRegs`). `__main__` מריץ את `T4_plc_flush`, לא את זה. נשאר בקוד כהיסטוריה.

## 6. ניהול עבודה — `GetNewJob(value)` (שורות 571–641)
- מאמת פורמט מספר הזמנה, שולף שורת עבודה מ-SQL (מק"ט, מפרט, גבולות עובי).
- מעדכן את כותרת העבודה ב-`Job_settings`.
- טוען את מפרט ה-MV (`mv.GetSpec`) מתיקיית `Cfg.MvFolder`.
- **מעדכן את גבולות העובי** (`thickness_min_mm`/`thickness_max_mm`) בתוך `config/config457_thk.json`, כך שמודול העובי יקרא אותם בהרצה הבאה.
- `GetNewJob_OLDREV` (שורה 514) — גרסה ישנה, לא בשימוש מה-UI.

## 7. `EL_UI` — חלון הראשי (שורות 654–1510)
חלון Tkinter בגודל קבוע (1650x850). הבנייה ב-`_build_ui` (1055): לוגו, כותרת עבודה לחיצה (פותחת New Job), אינדיקטור PLC, שלושה לוחות (Info / Image Analysis / Thickness), ושורת כפתורים תחתונה.

מתודות עיקריות:
- `NewJob` (670) — דיאלוג הזנת הזמנה חדשה עם ולידציה ב-Enter (קורא ל-`GetNewJob`).
- `_open_settings_screen` (823) — דיאלוגים גנריים (Engraving / Camera).
- `_open_thickness_adjustment_screen` (876) — עריכת **כל** מפתחות `config457_thk.json` בטופס, מוגן בסיסמה (`Cfg.Password`). Save/Reload/Close.
- `_open_modify_settings` (1135) — עריכת סקלרים של `Job_settings` + שדות `Cfg`.
- `_info_block` / `_analysis_block` / `_thickness_block` (1277/1380/1399) — שלושת הלוחות.
- `_update_t1_packjob_view` (1303) — טבלת pack-jobs + תמונה.
- `_update_plc_indicator` (1432) — אייקון/טקסט OnLine/OffLine לפי `Cfg.plc_connected`.
- `_on_close` (1423) — עוצר מסוע/אורות, מסמן `stop_event`, סוגר.

### `_refresh_from_Job_settings()` (שורות 1448–1492) — *שונה (תיקון קיפאון)*
לולאת הרענון של ה-UI, מתזמנת את עצמה כל 200ms עם `self.after`.
- **התיקון:** כל הגוף עטוף ב-`try/except`, וה-`self.after(200, ...)` נמצא ב-`finally` — כך ש**כשל בפריים בודד לעולם לא יכול להקפיא את ה-UI** (קודם, חריג כלשהו לפני שורת ה-after היה הורג את הלולאה לתמיד). שגיאה נרשמת כ-`WARN`.
- כל `pilN` נלקח ל-snapshot מקומי פעם אחת לפני ההמרה ל-`ImageTk.PhotoImage`, כדי לסגור מרוץ check-then-use מול ה-threads היצרנים.

## 8. `__main__` (סוף הקובץ)
מפעיל `t4, t1, t2, t3` (בסדר הזה), ואז `app = EL_UI(); app.mainloop()`. בסיום קורא `Job_settings.stop_event.set()`.

# חלק ג' — מודול העובי `thickness_Module_V3_w.py` (985 שורות)

מודול headless שקולט UDP משני חיישנים, מחשב עובי, ומספק לקוד הראשי תמונה + מדדים + קוד תוצאה. **המודול עצמו לא נוגע בבקר** — השליחה כולה דרך הקוד הראשי.

## 1. ייבואים ועזרים (שורות 1–125)
- `socket/struct/threading/queue/deque/numpy` — רשת, מקבילות, חישוב.
- `matplotlib` עם backend `Agg` — רינדור גרף הפרופיל ללא מסך.
- `_load_icon_png` (18), `get_fonts` (37) — אייקונים ופונטים לרינדור (cache).
- `_rtl_visual` (72) — היפוך טקסט עברי לתצוגה נכונה ב-PIL (PIL לא תומך RTL).
- `load_config_json` (105) — טעינת ה-JSON.
- `parse_push_packet` (114) — פענוח חבילת UDP: דילוג על 14 בייט header, פענוח int32 big-endian, המרה ל-mm (`/1e6`).

## 2. `ThicknessConfig` (שורות 127–163) — *שונה*
טוען פרמטרים מ-dict (שמקורו ב-`config457_thk.json`). `req()` זורק שגיאה ברורה אם מפתח חובה חסר. שדות עיקריים: `SENSORS, SOCKET_TIMEOUT, FRAME_INTERVAL_SEC, TIME_SYNC_THRESHOLD, LIVE_UPDATE_HZ, REFERENCE_HEIGHT_MM, SENSOR_DISTANCE_MM, ERROR_THRESHOLD_MM, AXIAL_SPAN_MM, THICKNESS_MIN/MAX, MAX_ERROR_COUNT, TARGET_POINTS, TRIM_LO/HI, P2P_THRESH_UM, CONICITY_THRESH_UM, NOMINAL_THICKNESS_MM_DEFAULT, TOL_UM_DEFAULT`.
- **שונה:** הוסרו השדות `PLC_IP` / `PLC_PORT` (לא רלוונטיים עוד — המודול לא מתחבר לבקר).

## 3. `ThicknessRuntimeState` (שורות 165–206) — *שונה*
מצב הריצה המשותף בין החיישנים למעבד.
- `samples` — שתי `deque` (TOP/BOTTOM) של `(timestamp, abs_mm)`.
- `object_in_measurement`, `start_time`, `sample_count`, `error_count` — מצב המדידה הנוכחית.
- `passes` — רשימת כל ההכרעות שהושלמו (גדלה, monotonic).
- `ui_queue` — תור אירועים ל-UI.
- `err_hist_um` — היסטוריית 60 השגיאות האחרונות (לעקומת הפעמון ב-gauge).
- `nominal_thickness_mm` / `tol_um` — נומינלי וטולרנס נוכחיים (תחת `nominal_lock`).
- **שונה:** הוסר כל קוד יצירת ה-`PLCWriter` (`self.plc`).

## 4. `SensorReader` (שורות 214–259)
thread לכל חיישן. קורא UDP, מפענח, ו**מתייג זמן ב"שעון וירטואלי"**: במקום `time.time()` (שגורם ל-clumping תחת עומס CPU), מקדם שעון פנימי ב-`FRAME_INTERVAL_SEC/num` לכל דגימה, עם anchor חד-פעמי ל-host. כל דגימה מתורגמת ל-`REFERENCE_HEIGHT_MM + v_mm` ונדחפת ל-`samples`.

## 5. `ThicknessProcessor` (שורות 261–471) — *שונה*

### `run()` (273)
- **מסנכרן** את הדגימות הראשונות של TOP/BOTTOM לפי הפרש זמן (`TIME_SYNC_THRESHOLD`); אם פער גדול מדי — זורק את המוקדמת.
- מסנן "ריק" (שני הצדדים מעל `ERROR_THRESHOLD_MM`) וסופר שגיאות; ברצף `MAX_ERROR_COUNT` בזמן מדידה → סוף עצם.
- מחשב `thickness = SENSOR_DISTANCE_MM - (top+bot)`. אם בטווח `THICKNESS_MIN..MAX` → מתחיל/ממשיך מדידה, צובר דגימות, ודוחף עדכון "live" ל-`ui_queue` בקצב `LIVE_UPDATE_HZ`.
- **שונה:** הוסרה כתיבת ה-PLC לתחילת מדידה.

### `process_end_of_measurement()` (331) — *שונה*
מחושב פרופיל סופי לעצם:
- חיתוך קצוות (`TRIM_LO/HI`) וצמצום ל-`TARGET_POINTS` נקודות ממוצעות.
- `mean_thickness`, `mean_err_um` (מול הנומינלי), `p2p_um`.
- **קוניות**: ממוצע 3 נקודות ראשונות פחות 3 אחרונות (חתום, ב-µm).
- הכרעות: `ok_nominal` (|שגיאה| ≤ טולרנס), `ok_conicity` (|קוניות| ≤ סף). `status="תקין"` רק אם שניהם תקינים.
- `fail_reason` — סיבת הפסילה בעברית: `"גבוה מהנומינלי"` / `"נמוך מהנומינלי"` / `"קוניות גבוהה"`.
- **חדש — `plc_code`**: קוד תוצאה יחיד לרגיסטר 5, מחושב **באותם תנאים בדיוק** כמו `fail_reason` (כך שהקוד והסיבה תמיד מסכימים):
  - `1` = תקין
  - `2` = עובי נמוך מהנומינלי (`mean_err_um < 0` מעבר לטולרנס)
  - `3` = עובי גבוה מהנומינלי (`mean_err_um > 0` מעבר לטולרנס)
  - `4` = קוניות גבוהה
  - נשמר במילון ה-`pass` כ-`"plc_code"`.
- **שונה:** הוסרה כתיבת ה-PLC (OK/NOK) — הקוד רק נשמר ב-`pass` ונחשף לקוד הראשי.

## 6. `ThicknessModule` — ה-API הציבורי (שורות 473–530) — *שונה*
זה מה שהקוד הראשי משתמש בו.
- `__init__` — טוען קונפיג, יוצר state, reader לכל חיישן, ומעבד. **חדש:** `self._last_reported_pass = 0` (למעקב edge detection).
- `start()` / `stop()` — מפעיל/עוצר את ה-threads. **שונה:** הוסרה סגירת ה-PLC ב-`stop()`.
- **חדש — `poll_new_result_code()`** (507): מחזיר את `plc_code` של ה-pass האחרון **רק אם הושלם pass חדש** מאז הקריאה הקודמת (משווה `len(passes)` ל-`_last_reported_pass`); אחרת `None`. כך הקוד הראשי כותב לבקר בדיוק פעם אחת לכל עצם.
- `get_display_image()` — מחזיר תמונת פאנל בלבד.
- `get_ui_packet()` — מחזיר `(image, mean_mm, p2p_um, conicity_signed_um)` כחבילה מסונכרנת (זה מה ש-T3 קורא).
- **חדש — API כיול:** `measure_gauge()`, `compute_and_apply_calibration()`, `get_calibration()`, `_save_calibration()`. ראה **חלק ד'**.

## 7. `get_display_payload` (שורות 538–658)
בונה את כל מה שצריך לתצוגה מתוך `last_n` ה-passes האחרונים: ממצע פרופילים על ציר זמן משותף (עם `np.interp` בעת הצורך), ומחזיר dict עם פרופיל, ממוצע, שגיאה, סטטוס, נומינלי/טולרנס, קוניות, ו-`fail_reason`.

## 8. שכבת הרינדור (שורות 626–984)
מחזירה תמונת PIL אחת לכל הפאנל (ה-UI לא יודע דבר על הנתונים הגולמיים):
- `_profile_plot_pil` (626) — גרף עובי מול זמן עם קווי נומינלי/טולרנס.
- `_gauge_pil` (682) — מד עם פס צבעוני (ירוק/צהוב/אדום), מחוג, ועקומת פעמון מהיסטוריית השגיאות.
- `_compute_big_status_lines` (788) — טקסט סטטוס גדול בעברית (כולל תיקון מומלץ במ"מ).
- `render_thickness_panel_pil` (846) — מרכיב הכל: 4 ריבועי אינדיקציה (מקבילות/קוניות/נומינלי/ממוצע), סטטוס גדול, gauge, גרף, ושורת סטטוס תחתונה.

## 9. זרימת נתונים במודול
```
חיישן UDP → SensorReader (שעון וירטואלי) → samples[TOP/BOTTOM]
         → ThicknessProcessor.run (סנכרון + עובי) → צבירה לעצם
         → process_end_of_measurement (פרופיל + הכרעה + plc_code) → passes[]
         → ThicknessModule: get_ui_packet (תמונה+מדדים) , poll_new_result_code (קוד)
         → הקוד הראשי (T3)
```

# חלק ד' — כיול מערכת העובי (Two-Gauge Calibration)

מנגנון כיול שמופעל **שרירותית ע"י המשתמש** (מה-HMI/בקר), מודד שני מדידי דיוק בעובי ידוע, ומתאים תיקון לינארי שמיושם על כל מדידה:
```
thickness_corrected = a · thickness_raw + b
```
ברירת מחדל לפני כיול: `a=1, b=0` (no-op). **ההנעה הפיזית באחריות הבקר/HMI — הקוד רק מודד, מחשב, ומדווח.**

## העיקרון
שני מדידים בעובי ידוע נותנים שתי נקודות `(raw, known)` → התאמת קו ישר:
```
a (gain)   = (known_2 − known_1) / (raw_2 − raw_1)
b (offset) = known_1 − a · raw_1
```
מאחר שהחיישנים קבועים זה מול זה, העובי **אדיש למיקום האנכי** של המדיד — לכן המדידים יכולים לשבת בקצה הטווח. ה-gain אמור להישאר ≈1; חריגה ממנו = אזעקת כשל (מדיד שגוי / תקלת חיישן).

## חלוקת אחריות
| איפה | מה |
|------|-----|
| `thickness_Module_V3_w.py` | `measure_gauge()` (מדידה סטטית בחלון זמן + בדיקת יציבות), `compute_and_apply_calibration()` (התאמה + ולידציה + החלה חיה + שמירה ל-JSON), `get_calibration()`; החלת התיקון בנקודה אחת ב-`ThicknessProcessor.run` |
| `457_test.py` (T3) | מכונת המצבים של ההאנדשייק מול הבקר; מפרסם את מצב הכיול ל-`Job_settings.thk_cal` |
| `457_test.py` (`EL_UI`) | חלון כיול ייעודי שנפתח אוטומטית ומציג מצב + נתונים חיים |
| `config/config457_thk.json` | בלוק `"calibration"`: עובי המדידים, חלון הזמן, ספי יציבות/gain, וערכי `a/b` הנשמרים |

## בלוק הקונפיג (`config457_thk.json`)
```json
"calibration": {
    "gauge_1_known_mm": 1.500,
    "gauge_2_known_mm": 2.500,
    "window_sec": 3.0,
    "stability_max_std_um": 5.0,
    "gain_min": 0.95,
    "gain_max": 1.05,
    "a": 1.0,
    "b": 0.0
}
```
הכל אופציונלי — אם הבלוק חסר, מתקבלות ברירות מחדל וה-`a/b` נשארים נייטרליים. אחרי כיול מוצלח נשמרים גם `raw_g1_mm`, `raw_g2_mm`, `last_calibration_iso`.

## פרוטוקול ה-handshake (שני רגיסטרים; חישוב אוטומטי אחרי מדיד 2)
**בקר → Py** ב-`RegsFromPlc[CAL_CMD_REG]` (=24): `1`=במדיד 1 מדוד, `2`=במדיד 2 מדוד, `0`=idle. *(אין פקודת "חשב" — החישוב אוטומטי בסיום מדיד 2.)*
**Py → בקר** ב-`RegsToPlc[CAL_STAT_REG]` (=13, **רגיסטר ייעודי, נפרד מתוצאת העובי ברגיסטר 5**): `1`=מודד (אל תזוז), `2`=מדיד 1 הסתיים (אפשר לזוז), `3`=כיול תקין, `4`=כיול נכשל, `0`=idle.

**זרימה:** הבקר מזיז למדיד 1 → כותב `1` → T3 מודד (3s) → רגיסטר 13 = `2` → הבקר מזיז למדיד 2 → כותב `2` → T3 מודד → **מחשב/מאמת/שומר אוטומטית** → `3`/`4` → הבקר כותב `0`. כשל בכל שלב (`4`) = הפסקת הרצף.

## חלון הכיול ב-UI
אותו חלון משרת שני מצבים, וכך המסך הראשי נשאר נקי:
- **רצף כיול חי:** נפתח אוטומטית כשהבקר מתחיל רצף (`Job_settings.thk_cal["active"]=True`), מתעדכן מלולאת הרענון (thread ראשי — Tkinter לא thread-safe), ומציג שורת מצב צבעונית, ה-raw+יציבות של כל מדיד, ה-`a/b` הסופי, והודעת כשל אם רלוונטי.
- **צפייה ידנית:** כפתור **"Calibration"** בשורת הכפתורים התחתונה (`_open_view_calibration`) קורא את הכיול האחרון מ-`config457_thk.json` (`a`, `b`, `raw_g1`, `raw_g2`, `last_calibration_iso`) ופותח את החלון במצב צפייה. אם הבקר מתחיל רצף בזמן שהחלון פתוח — אותו חלון מתחיל לקבל עדכונים חיים.

המסך הראשי לא מציג שום מידע כיול (במכוון — להפחתת עומס על המפעיל). כל מידע הכיול נגיש דרך הכפתור.

## הערה חשובה — סטטוס כ"פעימה"
`T4` מאפס את `RegsToPlc` אחרי כל שליחה, ולכן **כל ערך — כולל סטטוס הכיול — הוא פעימה חד-פעמית**, לא ערך "נדבק". זה עקבי עם רגיסטר 5 ושאר המערכת. **הבקר חייב לתפוס (latch) את הסטטוס במעבר**, לא להניח שיישאר. אם נדרש סטטוס נדבק — זה שינוי קטן ב-T4.
